Chapter 05

Runtime Execution and Blueprint Wiring

Where the flow actually runs, how your level talks to it, and how it talks back. Everything on this page is Blueprint-callable. You do not need C++ to wire any of it.

Name mapping

If your spec calls for ReportActionCompleted(Tag) and SendCustomPayload, those are the same idea as SimFlow's Broadcast Flow Event and its Payload pin: one call carries both the tag and the object. Delegates named OnStepStarted, OnStepCompleted, OnStepFailed and OnRuleViolation map to On Task Started, On Task Finished (which carries the result, so failure is a branch on that pin rather than a separate dispatcher) and On Mistake Recorded. The mapping is spelled out in the table at the end of this chapter.

Attaching the component

Add Component → SimFlow Component. The interesting decision is which actor hosts it. Get that right early, because moving a flow later means moving every binding with it.

Host actor by scenario shape
HostSuitsWatch out for
Game Mode A single-player scenario that owns the whole session. Exists before the level's actors do, which is an advantage for setup and a reason to prefer Auto - On First Tick over On Begin Play.
Level actor A flow tied to one room, rig or machine. Dies with the level. Fine for per-area drills, wrong for anything that must survive a travel.
Game State Multiplayer, one shared scenario everyone sees. The recommended home with Replicate Flow on, because the host actor has to replicate itself.
Player State Multiplayer, one independent flow per trainee. Also replicates properly. Each trainee gets their own blackboard and score.
VR pawn Flows that follow the player between levels. The pawn may respawn, taking the flow with it. Prefer Player State if respawning is possible.

The Level Blueprint is a workable place to bind to a component, but a poor place to host one. It cannot be reused across levels and it is awkward to reference from widgets. Put the component on an actor and let the Level Blueprint find it.

Start Mode

Manual waits for you to call Start Flow. Auto - On Begin Play starts on BeginPlay, Auto - On First Tick on the first tick after it, and Auto - After Delay waits Auto Start Delay seconds.

Prefer On First Tick over On Begin Play

On BeginPlay, other actors in the level may not have begun play yet, so a flow that immediately goes looking for a zone or an item can fail to find it. By the first tick every actor has begun play. There is a second reason too: if you bind dispatchers in your own BeginPlay, an On Begin Play start can fire On Flow Started before your bindings exist.

Switching the active procedure at runtime

Three approaches, in order of how often you will want them.

  1. Same asset, different entry

    Call Start Flow From Entry with the name of another Start node. One asset can hold a training entry and an evaluation entry, or a short and long version of the same drill. Nothing needs reloading.

  2. Different asset

    Call Stop Flow, set Flow Asset to the new asset, then Start Flow. Do the stop first. Swapping the asset under a running flow does not migrate the instance, and the running copy keeps its old nodes because they were duplicated at start.

    The blackboard goes with the instance. If the next procedure needs values from the last one, read them out before stopping, or compose the two with a Sub Flow instead.

  3. Composed, with Sub Flow

    For a sequence of procedures that share state, do not switch assets at all. Author a parent flow with Sub Flow nodes and let the blackboard merge between parent and child. This is the approach that survives a save and reload cleanly.

Pushing events from the world into a flow

Three entry points. All Blueprint-callable; the two statics take a world context, which Blueprint supplies for you.

Raising an event
CallReachesUse when
Broadcast Flow Event (Tag, Payload) Every running flow The usual case. A prop does not know which flow is running, and should not have to.
Send Flow Event (Flow Save Id, Tag, Payload) One specific flow Several flows are running and only one should hear it. Requires Flow Save Id to be set on the target component.

The payload must be an Actor or an Actor Component

An Actor Query accepts an Actor, or an Actor Component that it unwraps to its owner. Anything else scores No Match and logs a warning naming the class. Broadcasting self from a UMG widget graph is the single most common first bug in the plugin, because a UUserWidget is neither.

Tags and child matching

These native tags ship with the plugin and need no setup:

Add your own tags in Project Settings → Project → Gameplay Tags, or inline from any tag picker. Keep them in your own namespace rather than under SimFlow., because that hierarchy belongs to the plugin and a future version may add to it.

The component exposes nine Blueprint-assignable dispatchers. In your Blueprint, get the SimFlow Component and drag off Assign On Task Started and the rest; they appear as red event nodes.

Two more on the flow instance

Call Get Flow Instance on the component to reach these. The instance mirrors all nine above and adds:

Additional dispatchers on USimFlowInstance
DispatcherPinsUse for
On Event RaisedEvent Tag, PayloadReacting to any event the flow received, including ones no task was waiting for.
On Mistake RecordedMistakeThe rule-violation hook. This is where a warning message, a red flash or a haptic pulse comes from.

Two other objects broadcast as well. The blackboard has On Value Changed (Key, New Value), which fires on every write and is the right way to drive a live score widget without polling. A SimFlow Zone has On Actor Entered, On Actor Exited and On Actor Settled, the last being the one tasks themselves listen to.

Bind before the flow starts

A missed first event usually means a binding race

With Start Mode set to Auto - On Begin Play and your bindings made in your own BeginPlay, On Flow Started and often the first On Task Started can fire before the bindings exist. Use Auto - On First Tick, or keep Manual and call Start Flow yourself after binding.

Two load modes

Exact State restores the exact set of active nodes, elapsed times included.

From Last Checkpoint restores the blackboard and re-runs the flow from the last checkpoint the trainee passed. This is the friendlier option for a training session resumed the next day.

Object references in the blackboard are stripped on save, by design. A blackboard key holding an actor will be null after a load, so store an identity tag or a name if you need to re-resolve it.

Multiplayer wiring

  1. Host the component on a replicating actor

    Game State for a shared scenario, Player State for one flow per trainee. Tick Replicate Flow. The owning actor must replicate itself, which is the whole reason those two are recommended.

  2. Add a SimFlow Player Component to the PlayerController

    Without it a client has no route to the server, and client control calls do nothing at all. This is the single most common multiplayer setup miss.

  3. Set Flow Save Id

    It addresses the flow over the network as well as inside a save file. Request Flow Control and Send Flow Event both target by it.

  4. Drive client UI from replicated state

    Bind On Net State Changed and read the query functions. Leave Replicate Blackboard on if client widgets need score or answers.

    Instructor panels should call Request Flow Control (a static taking Flow Save Id and a control request). It takes the right route automatically: straight through on the server, via a server RPC on a client.
