Chapter 04

Rules, Out-of-Order Handling and Failure Policies

This is the part of SimFlow that separates a training scenario from a scripted demo. A trainee who does the right thing at the wrong moment, or the wrong thing at the right moment, is the interesting case, and the plugin treats it as a first-class outcome rather than something you detect by accident.

Two policies, two situations

Wrong-action handling lives in two enums. Which one you are configuring depends on the task, not on a global setting.

Mismatch Policy

Used by Wait For Event and Place Object In Zone. Answers: the trainee acted on an object, and it was the wrong object.

Out Of Order Policy

Used by Ordered Sequence. Answers: the object is part of the procedure, but this was not its turn. Note the difference. This is a trainee who knows the steps and got the order wrong, which is a different error from grabbing a random prop.

Mismatch Policy values

Wrong Item Policy on Place Object In Zone, Mismatch Policy on Wait For Event
ValueBehaviourReach for it when
Ignore (Keep Waiting) Says nothing and keeps waiting. The wrong object is not the one we want. Free exploration, or a bay that props legitimately pass through.
Count Mistake (Keep Waiting) Records a mistake and keeps waiting, so the trainee can correct themselves. The default. Almost all training. It captures the error without stopping the run.
Count Mistake And Fail Task Records a mistake and fails, driving the Task node's Failed pin. Assessment, or a safety-critical step where the wrong object ends the attempt.

Out Of Order Policy values

Out Of Order Policy on Ordered Sequence
ValueBehaviourReach for it when
IgnoreIgnores anything that is not the expected step.Free exploration.
Count Mistake (Stay On Step)Records a mistake but holds on the current step. The default.Training. Let them find it.
Count Mistake And RestartRecords a mistake and sends the trainee back to step one.Procedures where a wrong order invalidates the result.
Count Mistake And Fail TaskRecords a mistake and fails, driving the Failed pin.Assessment.
Restart is stricter than it sounds

A single slip on step 5 of a seven-step procedure sends the trainee back to step 1. That is correct for a safety procedure where a wrong order invalidates everything, and merely infuriating everywhere else. Use it deliberately, not as a default.

Mapping the four outcomes people usually ask for

Requirements documents tend to describe four outcomes: ignore, warn, penalise, fail. Three of those are policy values. One is built from two settings.

Requested outcome mapped to actual configuration
You wantSetPlus
Ignore Policy to Ignore Nothing. No mistake is recorded and no counter moves.
Warning event Policy to Count Mistake (Keep Waiting) or Count Mistake (Stay On Step) Bind On Mistake Recorded on the flow instance. That dispatcher carries the mistake struct, which is where your warning text, screen flash or haptic pulse comes from.
Penalty point Policy to a Count Mistake value Set the task's Score On Failure to a negative number, or branch on the WrongAttempts blackboard key. Recording a mistake does not itself move the score.
Hard procedure fail Policy to Count Mistake And Fail Task Wire the Task node's Failed pin to a Finish node with a failure result. Leaving Failed unwired with Fallback To Completed on turns the fail back into a success.

How input is judged

For an Ordered Sequence, every event with a matching tag runs this ladder. Knowing the order explains why a given press was graded the way it was.

  1. Is it the expected step?

    An Exact Match against the current step's Target fires On Step Completed and advances. If that was the last step, the task finishes with Succeeded.

  2. Is it a different step in the sequence?

    Every other step's target is checked. This is what decides severity, and it is why a well-shaped tag tree pays off here.

  3. Is it unlisted?

    With Unlisted Input Is Mistake off, which is the default, unrelated input is ignored silently. That is the right behaviour when unrelated props share the tag.

  4. Otherwise the policy applies

    A mistake is recorded as SimFlow.Mistake.WrongOrder with a description such as "Step 2: used Valve One - expected Control.Valve.Three", and the WrongAttempts blackboard key is incremented.

Severity is graded, not binary

When a mistake is recorded, its severity reflects what kind of error it was:

  • Using a step of the procedure at the wrong moment is Related (Near Miss). They know the procedure and got the order wrong.
  • Grabbing a prop that was never part of it is No Match, a different kind of error entirely.

This distinction only exists if your tag hierarchy supports it. Confusable things have to share a parent. Control.Valve.One and Control.Valve.Three are near misses of each other. Valve1 and Valve3 as flat tags are not, and every wrong answer collapses to "completely wrong".

Min Related Tag Depth on the Actor Query, default 2, controls how many leading tag nodes have to agree before something counts as related.

What a mistake record carries

  • A kind tag, for example SimFlow.Mistake.WrongOrder.
  • The involved actor, and the display name used in the generated description.
  • A severity derived from match quality.
  • A timestamp.
  • The Task Id of the step it happened under.

Mistakes collect on the flow instance, which is what makes an end-of-run debrief possible without you logging anything yourself.

Scoring is opt-in and starts at zero

Score On Success and Score On Failure both default to 0.0 on every task, so a flow scores nothing until you set them. That is the whole answer to "why does Get Score always return 0". The failure value is usually negative.

Recovery paths

A policy decides what happens at the moment of the error. A recovery path decides where the trainee goes next, and that is graph wiring rather than a setting.

Three strikes, then remediation

The built-in tasks already increment WrongAttempts, so there is nothing to write yourself.

  1. Add a Branch after the task

    Right-click, then Flow Control → Branch.

  2. Add one case

    Label it Needs remediation. Set its Condition to Blackboard Compare, key WrongAttempts, operation >=, value Int 3.

  3. Wire the two routes

    The case pin goes to your remediation section. Default continues the normal path.

    Cases evaluate top to bottom and the first match wins. Put the most specific case first. A case whose condition slot is empty is treated as false, so it never fires and execution falls through to Default, silently.

Pass or remediate at the end of an assessment

Sending trainees who scored under 70 to a remediation section:

  1. Branch after the last task

    One case, Score Threshold, operation <, threshold 70.

  2. Wire the case to remediation, Default to the pass section

    That is the simple form.

  3. To require a score and a mistake ceiling

    Use All Of with two children, Score Threshold at >= 70 and Blackboard Compare on Mistakes at <= Int 2, and put that composite on the pass case rather than the remediation one.

    An empty All Of is true. Standard logic makes an empty AND pass and an empty OR fail, so a composite you added but never filled in passes every single time. If a composite behaves oddly, check it actually has children.

Prerequisite gates

A gate stops a step from being satisfiable until something else is true. SimFlow has three ways to express one, and they differ in where the wait happens.

Three ways to gate a step
MechanismWhere it sitsBehaviourUse for
Wait For Condition task Its own Task node Blocks until a condition becomes true. "Do not continue until the pressure is below 2 bar."
Branch with a condition A Branch node before the step Routes rather than waits. Evaluated once, on arrival. "Skip the donning section if they are already wearing gloves."
Abort Condition On the Task node, under Early Out Ends a running task early, leaving via Abort Result. Evaluated every frame. "Cancel this step if the trainee walks away."

Event Was Raised is the condition that turns a gate into a real prerequisite. It asks "has this tag been raised at any point in this run", reading the instance's event history rather than waiting live. Gate step 6 on Event Was Raised for the tag step 3 raises, and step 6 becomes unreachable until step 3 genuinely happened, regardless of the order the trainee attempted things in.

Gates are where circular dependencies appear

Gating A on B while B is gated on A produces a flow that stalls with no error, because Wait For Condition goes on waiting. Worse, a Sub Flow that calls itself, directly or through a cycle, hangs the editor on Play: there is no recursion guard. Draw the prerequisite graph on paper before wiring more than two gates.

Empty conditions are false, quietly

Worth memorising, because every one of these is a silent hang rather than an error:

  • A Branch case with no condition is false, so that case never fires.
  • A Wait For Condition with an empty Condition slot waits forever.
  • A Blackboard Compare whose key does not exist returns Result When Key Missing, default false. Change that setting when a check should pass on the first run, before anything has written the key.
  • An Event Was Raised with no tag is false, because an invalid tag was never raised.
  • An empty All Of is true. An empty Any Of is false.

Every condition also carries an Invert field, applied after the condition evaluates. An inverted All Of means "not all of them", not "none of them".

Step timeouts and countdowns

Timeouts live on the Task node, not on the task. One field and one pin:

Timeout behaviour
SettingEffect
Time Limit = 0No limit. A task waiting on something that never arrives blocks the flow forever.
Time Limit > 0The task leaves via Timed Out when the limit elapses.
Timed Out unwired, fallback onA timeout routes back to Completed and reads as success.
Auto Retry On TimeoutRestarts the task instead of leaving. Timed Out is only taken once the retries are used up.

The countdown resets on each retry, because auto-retry restarts the task and Elapsed Time restarts with it. For a live countdown in UI, read Get Current Task Remaining Time on the component. It returns -1 when the current task has no limit, which is the value your widget should treat as "hide the timer" rather than as zero.

Set a Time Limit on everything while developing

Even a generous one. Wire Timed Out to a Log Message task. A hang then becomes a message naming the task instead of a flow that silently stops, and finding a stall this way takes seconds rather than an afternoon.

Retry and skip need both layers to agree

The node and the task each get a say, and both have to allow it. This trips people up once.

On the Task node

  • Auto Retry On Failure
  • Auto Retry Limit
  • Auto Retry On Timeout

On the task, under Rules

  • Allow Retry, bool, default true: whether the player may retry through the component.
  • Max Retries, int, default 0: 0 is unlimited. Once exceeded, a retry request fails the task instead.
  • Allow Skip, bool, default true: whether the player or instructor may skip it.
  • Tick While Paused, bool, default false: leave it off unless you know you want it.

Turn on auto-retry at the node while the task's own Allow Retry is off and nothing retries. The task's rule wins. Automatic retry also happens inside the node: when the task fails, the node restarts it without leaving through any pin, and execution only leaves via Failed once the retries are used up.

Manual retry, skip and fail come from outside, through Retry Current Task, Skip Current Task and Fail Current Task on the component. Those are what an instructor panel calls. See Chapter 05.

Training mode against evaluation mode

There is no global mode switch in the plugin. "Training" and "evaluation" are combinations of the settings above, and the cleanest way to ship both is two flow assets, or one asset with two Start node entries routing into differently configured sections.

Build the drill once, wrap it twice

Author the procedure as one asset, then use Sub Flow nodes to run it inside a training wrapper and an evaluation wrapper. The wrappers differ in their branch logic, debrief and scoring; the drill itself stays single-source. The blackboard merges back into the parent, so the wrapper can read Score and WrongAttempts from the child run.
