Developer Guide

Save and Load Internals

Structs
FSimFlowSaveState, FSimFlowNodeSaveState
Container
USimFlowSaveGame, keyed by Flow Save Id
Authority
Server only. On a client, save and load log and return.

What a save contains

USTRUCT() struct FSimFlowSaveState
{
    FString                                FlowAssetPath;
    FName                                  FlowSaveId;
    ESimFlowRunState                       RunState;
    FName                                  EntryName;
    float                                  ElapsedTime;
    TArray<FSimFlowNodeSaveState>          NodeStates;
    TArray<FSimFlowBlackboardEntry>        Blackboard;
    FGuid                                  LastCheckpointGuid;
    TArray<FGameplayTag>                   RaisedEvents;
    FDateTime                              SavedAt;
    FString                                Label;
};

USimFlowSaveGame holds a TMap keyed by Flow Save Id, plus a free-form ExtraData array and a SaveVersion. Several flows share one slot, which is why Flow Save Id has to be set on any component you intend to save.

Scenario history is not in here

USimFlowScenarioSave is a separate USaveGame in its own slot, SimFlowScenarios by default, holding a TMap<FName, FSimFlowScenarioRecord> keyed by the same Flow Save Id a run save uses. Each record holds a play count, how the last attempt ended and when, and the best score the scenario has produced.

Keeping it out of USimFlowSaveGame is deliberate. A run save is cleared by Delete Flow Save and overwritten on every Quick Save, and a play count or personal best that disappeared when a trainee cleared their progress would be a bug rather than a feature. A submitted score replaces the stored one only when it is strictly higher. The nodes are on the scenario record page.

The two load modes differ in ordering

Exact State

Activates each node that was active, then calls LoadNodeState. Activating first lets the task run its start logic and reapply world setup; the counters are overwritten afterwards.

From Last Checkpoint

Restores the blackboard and re-enters the checkpoint node. Nothing mid-task is restored, because nothing mid-task was meant to be.

Activate first, then overwrite

That ordering is the reason a restored Wait For Event task is actually listening again rather than sitting inert with the right numbers on it. If you write a custom node that binds to anything in ExecuteInput, this ordering is what makes your bindings come back.

How a node participates

USTRUCT() struct FSimFlowNodeSaveState
{
    bool                    bActive;
    float                   ActiveTime;
    FName                   ActiveInputPin;
    int32                   IntState;
    TArray<FName>           ReceivedInputs;
    TArray<FSimFlowBlackboardEntry> CustomData;
};

Override SaveNodeState and LoadNodeState on your node. IntState is there for the common case of a single counter, which is what Loop uses for its iteration and Join uses for its arrival count. ReceivedInputs is what lets a Wait For All Join remember which pins already fired.

Tasks get ReceiveSaveTaskState and ReceiveLoadTaskState, with a SetSavedValue and GetSavedValue bag stored in FSimFlowNodeSaveState::CustomData. From Blueprint that bag is the whole API; you never touch the struct.

Two things that will bite

BehaviourConsequence
Object values are stripped Any blackboard key holding an actor is null after a load. Store a tag or a name and resolve it again. See the blackboard page.
Auto Save writes synchronously The SaveGame file is written on the game thread the moment a Checkpoint executes. Fine between stages, visibly janky inside a loop body.
