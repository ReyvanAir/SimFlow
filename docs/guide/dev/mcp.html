Developer Guide

Controlling SimFlow from Claude (MCP)

Where it lives
Content/Python/simflow_toolset, backed by USimFlowEditorLibrary
Needs
The engine's Unreal MCP and Toolset Registry plugins, both experimental. SimFlow works without them.
Scope
Editor and Play In Editor. Nothing reaches a packaged game.

An MCP client such as Claude Code can read, edit and run flows in the editor. It goes through the engine's own MCP server. SimFlow adds a toolset of 28 tools to it; there is no separate server to run.

Setup

Turn on Unreal MCP, Toolset Registry, Python Editor Script Plugin and Editor Scripting Utilities in the project. Then, in Project Settings > Model Context Protocol, tick Auto Start Server and restart the editor. The server listens on http://localhost:8000/mcp unless you changed the port or path there.

claude mcp add --transport http unreal http://localhost:8000/mcp
The server has no sign-in

Any process on the machine that can reach the port can call the tools, including the ones that edit and delete. Leave it off on a shared computer.

By default the server lists only list_toolsets, describe_toolset and call_tool, and the client looks up the rest as it needs them. The SimFlow toolset's name is simflow_toolset.toolset.SimFlowTools; a client passes it as toolset_name. Without Toolset Registry, init_unreal.py logs one line and registers nothing.

The tools

Assets are named by path (/Game/Flows/FireDrill), nodes by the guid describe_flow prints, and types by the names the list tools print (SimFlowNode_Task, or Node_Task). A Blueprint type needs its full path.

How an edit works

Each tool loads the asset, changes the runtime nodes inside one editor transaction, then calls SyncGraphFromAsset so the graph view matches. That is why an edit shows in an open editor tab and is one undo step. Nothing reaches disk until save_flow.

Settings travel as a JSON object keyed by the names describe_type gives. SetPropertiesFromJson checks every name first and refuses the whole call, naming the bad ones, if any is not an editable plain property. Otherwise it applies them and sends the same change notification the Details panel does, so a Branch rebuilds its pins.

A task or condition is created in its slot by class, with SetInstancedProperty. The slot is a path from the node: Task, Cases[1].Condition, Task.Condition. A path steps through structs, array elements and objects already in place, and ends at an object slot or at an array to append to. The new object is outered to the node that holds it, so it saves with the asset.

Setting an array replaces it

Writing a Branch's Cases from JSON builds new elements, and the conditions inside the old ones are gone. Set the cases first, their conditions after.

Adding a tool of your own

The toolset is a Python class deriving unreal.ToolsetDefinition. A tool is a static method under @toolset_registry.tool_call, with every parameter and the return value annotated and the docstring's Args and Returns filled in; the docstring becomes the description the client sees. Add it to SimFlowTools in simflow_toolset/toolset.py. If it needs something a script cannot reach, add a UFUNCTION to USimFlowEditorLibrary for it, as GetNodeGuidString was.

Tests

SimFlow.Editor.McpHelpers covers the C++ helpers. SimFlowToolset.Python runs simflow_toolset/tests through Epic's Python test runner: it builds, wires, reads back and breaks a flow through the same static entry points the server calls. Both run under Automation RunTests SimFlow. The Play In Editor tools have no automated test, because they need a running game.

Limits

  • Toolset Registry and Unreal MCP are experimental and 5.8 only. A later engine version may change the Python side.
  • Only editable settings are reachable. Runtime-only state is not.
  • A Blueprint task's settings appear when its variables are Instance Editable.
  • Nothing here works in a packaged game.
