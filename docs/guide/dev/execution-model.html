Execution Model

Class
USimFlowInstance
Shape
Queue driven, not recursive
Safety valve
MaxActivationsPerProcess = 10000
Re-entrant nodes
Join and Loop only

The one thing to internalise: TriggerNodeOutput enqueues a target rather than calling into it. Nothing recurses.

The activation queue

void USimFlowInstance::ProcessPendingActivations()
{
    if (bProcessingActivations) return;      // re-entrancy guard
    bProcessingActivations = true;

    while (PendingActivations.Num() > 0 && RunState == ESimFlowRunState::Running)
    {
        if (++Processed > MaxActivationsPerProcess) { bOverflowed = true; break; }
        const FPendingActivation Next = PendingActivations[0];
        PendingActivations.RemoveAt(0, 1, EAllowShrinking::No);
        if (USimFlowNode* Node = FindRuntimeNode(Next.NodeGuid))
            ActivateNode(Node, Next.InputPin);
    }

    bProcessingActivations = false;
    if (bOverflowed) { /* log, fail the flow */ }
}

Three consequences follow from that shape.

  • A chain of a thousand instant nodes costs one stack frame, not a thousand.
  • A runaway loop is caught at 10,000 activations per step and fails the flow with an error instead of hanging the editor.
  • Ordering stays breadth-first within a step.

ActivateNode refuses to re-enter a node that is already active unless it overrides AllowsReentrantActivation(). In the shipped set, exactly two nodes do: Join and Loop.

Dead ends complete the flow

If a node deactivates with no links, and nothing else is active or queued, the instance completes. That is what lets an unwired Completed pin end a simple flow cleanly rather than stalling it.

Pins and links

USTRUCT() struct FSimFlowPinLink   { FGuid NodeGuid; FName PinName; };
USTRUCT() struct FSimFlowOutputPin { FName PinName; FString DisplayName;
                                     TArray<FSimFlowPinLink> Links; };
USTRUCT() struct FSimFlowInputPin  { FName PinName; FString DisplayName; };

Nodes store their own pins and their own outgoing links. The editor graph is a view: on every change USimFlowGraph::CompileToAsset clears all links and rebuilds them from the visual connections. The runtime never reads the UEdGraph.

Well-known names live in namespace SimFlowPins: In, Out, Completed, Failed, Skipped, TimedOut, Default, LoopBody. Use them instead of string literals. Loop's Continue pin is USimFlowNode_Loop::ContinuePin.

Rebuilding pins

RebuildPins() is non-virtual and follows a template method pattern: stash existing links, clear the arrays, call the virtual BuildPins(), then restore links onto any pin whose name still exists.

void USimFlowNode_Task::BuildPins()
{
    AddInputPin(SimFlowPins::In);
    AddOutputPin(SimFlowPins::Completed);
    AddOutputPin(SimFlowPins::Failed);
    AddOutputPin(SimFlowPins::Skipped);
    AddOutputPin(SimFlowPins::TimedOut);
}
Override BuildPins, never RebuildPins

Because links are preserved by name, changing a Branch's case count keeps the wires on cases that still exist. Overriding the wrong one loses that.

Three ways to leave a node

TriggerOutput(SimFlowPins::Completed);                       // leaves and deactivates
TriggerOutput(SimFlowPins::LoopBody, /*bStayActive*/ true);  // fires, stays active
FinishNode();                                                // deactivate, go nowhere

bStayActive matters for nodes that must survive their own output. Loop keeps running while the body executes, and a Wait For Any Join stays alive to absorb the losing branch.

Menu labels come from the CDO

GetNodeCategory() places the node in the right-click menu, and the label is the class default object's GetNodeTitle(). That is why the Finish node lists as "Complete Flow".
