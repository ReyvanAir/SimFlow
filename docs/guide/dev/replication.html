Developer Guide

Replication

Structs
FSimFlowNetState, FSimFlowNetTask
Model
Server-authoritative, with client mirroring
Switch
bReplicateFlow. Off by default.
Bandwidth
Flat with respect to graph size

The design constraint: clients already have the flow asset. So the wire never carries nodes, tasks, conditions or display text. It carries Guids, and the client resolves them locally.

What crosses the wire

UPROPERTY(ReplicatedUsing = OnRep_NetState)
FSimFlowNetState NetState;

UPROPERTY(ReplicatedUsing = OnRep_Blackboard)
TArray<FSimFlowBlackboardEntry> ReplicatedBlackboard;   // gated by bReplicateBlackboard

FSimFlowNetState carries the run state, the active node Guids, an FSimFlowNetTask per active task (Guid, start server time, time limit, retry count), progress, elapsed time and bHasEverStarted.

Nodes, tasks and conditions never replicate. A client resolves a Guid back to the authored node and reads display names, instructions and quiz content out of its own copy of the asset. Add fifty nodes to a flow and the bandwidth does not move.

Elapsed time alone does not dirty the state

UpdateNetState compares with EqualsIgnoringTime, so a running clock does not push an update every frame. A periodic refresh on NetRefreshInterval keeps it from going stale. That is why a client countdown should interpolate locally rather than display the replicated value raw.

Authority gating

bool HasFlowAuthority() const
{
    if (!bReplicateFlow) return true;              // single player: everyone
    const AActor* Owner = GetOwner();
    return !Owner || Owner->HasAuthority();
}

TickComponent early-outs on a mirror. Control functions check IsClientMirror() and forward to the server through the local USimFlowPlayerComponent.

Presentation events go out as NetMulticast, Reliable RPCs carrying a node Guid. ShouldMulticastEvents() decides between multicasting and firing locally, so standalone and dedicated-server paths each fire every delegate exactly once.

The client to server control channel

A flow hosted on the Game State has no owning connection, so a client cannot RPC to it directly. USimFlowPlayerComponent lives on the PlayerController and relays instead.

USimFlowPlayerComponent relays
FunctionCarries
ServerRequestControlFlow Save Id plus an ESimFlowControlRequest.
ServerRequestQuizAnswerFlow Save Id, quiz node Guid, option index.
ServerRequestEventFlow Save Id, gameplay tag, payload.

Each request resolves its target by Flow Save Id and then passes through server-side authorisation:

virtual bool IsRequestAuthorised_Implementation(
        USimFlowComponent* TargetFlow,
        ESimFlowControlRequest Request) const;

It is a BlueprintNativeEvent, so override it for instructor-only controls. bRestrictToOwnedFlows is the built-in default gate.

No Player Component means client controls do nothing

Silently. There is no route to the server and nothing logs an error at the call site. It is the most common multiplayer setup miss, and worth asserting in your own PlayerController if you ship to a team.

Where the component has to live

The owning actor must replicate itself. Game State for one shared scenario, Player State for one flow per trainee. A level actor that does not replicate will mirror nothing no matter what bReplicateFlow says.

Current limits

  • Blackboard replication resends the whole array. Fine for tens of keys at tutorial pacing; move to a FastArraySerializer beyond that.
  • Presentation multicasts are reliable. Right for a flow that changes task every few seconds, wrong for high-frequency events.
  • Object values never cross the wire, for the same reason they are never saved.
