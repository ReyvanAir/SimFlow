Task Reference

Place Object In Zone Task

Class
USimFlowTask_PlaceObject
Select via
Task node → Task dropdown → Place Object In Zone
Finishes with
Succeeded at Required Count; Failed immediately if the zone cannot be resolved
Hard dependency
A SimFlow Zone actor in the level
Category
Object handling

Use it for: "Put the foam extinguisher in the bay." This task watches a zone and judges what turns up in it.

The zone reports what is there without any opinion about right and wrong. The task holds the opinion. That split is why the same bay can be the correct answer in one exercise and a distractor in the next, without touching a single Blueprint. The task also grades how wrong a wrong answer was, so your feedback can say "close, that is the CO2 unit" rather than just "no".

Fields

The four that matter
FieldTypeDefaultMeaning
ZoneActor QueryemptyWhich zone to watch. Usually a tag like Zone.PartsBin, or the zone actor itself.
Accepted ItemsActor QueryemptyWhat belongs there. Tags are the useful form, because they cover spawned copies.
Required CountInt, min 11How many accepted items must be in the zone at once.
Wrong Item PolicyEnumCount Mistake (Keep Waiting)What happens when the wrong thing is placed.

Two queries and two choices is the whole task. The rest is behind the Advanced arrow, and most drills never touch it.

Under Advanced
FieldTypeDefaultMeaning
Rejected ItemsActor QueryemptyExplicit wrong answers, always treated as a mistake.
Require SettledBooltrueWait for the item to be put down and let go, rather than reacting while it is still held.
Report Each Wrong Item OnceBooltrueReport a given wrong item once, not every time it re-settles.
Placed Item Blackboard KeyNameNoneStores the last accepted item.

Plus the fields every task has.

The two empty-field failures look nothing alike

Fails at once, or never completes

Leave Zone empty and the task fails immediately: at start it logs "could not resolve a SimFlow Zone from its Zone query" and finishes with Failed, driving the Task node's Failed pin. No waiting, no retry.

Leave Accepted Items empty and the task starts perfectly happily, then never completes. An empty query scores No Match against everything, so every item placed is judged wrong, in silence, forever.

So: if the task fails at once, check the Zone. If it never completes, check Accepted Items.

Leaving Rejected Items empty is the normal case. With it empty, anything Accepted Items does not match is already wrong. Fill it in only to carve one item out of a family you otherwise accept.

A few related traps. A tag in the Zone query is matched against the level's SimFlow Zone actors only, so a prop wearing the same tag is ignored rather than winning the lookup and failing the task. Two zones sharing a tag is still ambiguous: the first world match wins and which one that is is undefined, so give them distinct tags. Pointing Specific Actor at something that is not a zone does still fail at start, because naming the wrong actor outright is a different mistake from a tag that happens to be shared. A Required Count higher than the number of items that exist can never be satisfied. And Require Settled with held state unwired may mean items never settle at all if your VR framework holds them by constraint; with it off, the task reacts the instant an item overlaps, including while it is still in the trainee's hand.

How an item is judged

When the zone reports an item as settled, or merely contained with Require Settled off, the task grades it.

The item is graded against Accepted Items, giving Exact, Related or No Match. That grading is the whole story when Rejected Items is empty, which is the normal case: anything that is not an Exact match is a wrong item.

Rejected Items only vetoes an accept

An item matching it can never be Exact, even when Accepted Items would have let it through; it drops to Related. It cannot promote anything, so an item that was already No Match stays No Match. Listing Item.Wrench there does not make a wrench a near miss. How wrong a wrong answer is remains a question about the tags.

An Exact match is stored to Placed Item Blackboard Key if you set one, fires On Correct Item Placed, and re-counts the zone. Anything else fires On Wrong Item Placed with the match quality, builds a mistake description ("Placed CO2 Extinguisher in Extinguisher Bay - expected Item.Extinguisher.Foam"), and applies the Wrong Item Policy.

Counting, and what that implies

The task re-counts on every settle and finishes with Succeeded when the number of Exact-matching items currently in the zone reaches Required Count.

Because it counts what is there now rather than what has ever been there, two things follow. The right item already sitting in the zone when the task starts counts immediately, since the task evaluates the zone contents at start. And taking a correct item back out decrements the count again.

Re-reporting a wrong item

With Report Each Wrong Item Once on, which is the default, a wrong item is reported once. Taking it back out of the zone clears that memory, so putting it back tells them again. That is deliberate: a repeated mistake is worth repeating the feedback for.

What it needs to work

  • A SimFlow Zone in the level. This is a hard dependency; the task fails without one.
  • Identity components on the items, for tag-based queries.
  • Held state wired up, if Require Settled is on and your framework does not reparent on grab.

The right extinguisher in the bay

The trainee must put the foam extinguisher in the bay. The CO2 unit is a plausible wrong answer that should be called out specifically.

Setting up the world

  1. Add the tags

    In Project Settings → Gameplay Tags, add Zone.ExtinguisherBay, Item.Extinguisher.Foam and Item.Extinguisher.CO2.

  2. Place and name the zone

    Place a SimFlow Zone at the bay, size its Box, and set its identity tags to Zone.ExtinguisherBay with Display Name Extinguisher Bay.

  3. Give the props an identity

    On BP_Extinguisher_Foam, add a SimFlow Identity with Item.Extinguisher.Foam and Display Name Foam Extinguisher. Same for the CO2 one.

  4. Wire held state

    In your grab logic, call Set Held(true) on grab and Set Held(false) on release.

    Attachment alone is unreliable in VR. Many frameworks hold by physics constraint, in which case nothing ever settles until held state is wired.

Setting up the task

  1. Add the task

    A Task node with Task set to Place Object In Zone.

  2. Point it at the zone and the answer

    Zone → Required Tags of Zone.ExtinguisherBay. Accepted Items → Required Tags of Item.Extinguisher.Foam.

  3. Leave the rest alone

    Required Count at 1. Nothing under Advanced needs touching.

  4. Choose the wrong-item behaviour

    Wrong Item Policy of Count Mistake (Keep Waiting).

  5. Tell them, and score it

    Instruction of Place the foam extinguisher in the bay. Score On Success of 10.

  6. Give graded feedback

    Bind On Wrong Item Placed and switch on the match quality. Related gives "Close, that is the CO2 unit. You want foam." No Match gives "That does not belong in the extinguisher bay."

    The CO2 unit scores Related on its own, because it shares Item.Extinguisher with the accepted tag at the default Min Related Tag Depth of 2. No configuration needed.

Where Rejected Items actually earns its place

None of the above needed it. The field is for subtracting from an open-ended family: to accept any extinguisher except the CO2 one, set Accepted Items → Required Tags to Item.Extinguisher and Rejected Items → Required Tags to Item.Extinguisher.CO2. The veto makes the CO2 unit a mistake even though it matches the accepted tag, and the rule keeps holding when someone adds Item.Extinguisher.Water later.
