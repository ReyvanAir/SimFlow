Task Reference

Ordered Sequence Task

Class
USimFlowTask_OrderedSequence
Select via
Task node → Task dropdown → Ordered Sequence
Finishes with
Succeeded after the last step; Failed on an empty tag or the strictest policy
Category
Object handling

Use it for: "Press these three buttons, in this order." Every button broadcasts the same tag with itself as the payload and knows nothing about the procedure. This task holds the order.

The reason for a dedicated task, rather than a chain of Wait For Event tasks, is that acting out of turn becomes a first-class outcome instead of something you notice by accident. A chain of separate tasks would ignore a premature press. This one can tell the trainee they did the right thing at the wrong moment.

Each step holds a Target (an Actor Query, empty by default) naming the object that step expects, and an Instruction (multi-line text, empty) shown while it is the current step, readable with Get Current Step Instruction.

Plus the fields every task has.

No steps succeeds, no tag fails

The asymmetry is deliberate

An empty Steps array logs "has no steps - finishing immediately" and finishes with Succeeded. An empty Event Tag logs "has no event tag set - failing" and finishes with Failed. They are different kinds of mistake: an empty step list is a flow nobody has filled in yet, while a missing tag is a task that could never have worked.

A step whose Target is unset is a third case, and the worst of them: an unset query matches nothing, so the task hangs on that step with no complaint.

Two steps may share a target. The first press satisfies step 1, the second is judged against step 2 and advances, so repeating an object in a sequence works fine.

How input is judged

For every event with a matching tag, the task asks:

  1. Is it the expected step?

    An Exact match for the current step's Target fires On Step Completed and advances. If that was the last step, the task finishes with Succeeded.

  2. Is it a different step in the sequence?

    Every other step's target is checked. This is what decides severity.

  3. Is it unlisted?

    With Unlisted Input Is Mistake off, it is ignored silently. That is the default, and it is right when unrelated props share the tag.

  4. Otherwise, the policy applies

    The mistake is recorded as SimFlow.Mistake.WrongOrder with a description like "Step 2: used Valve One - expected Control.Valve.Three", and the WrongAttempts blackboard key is incremented.

    A payload that is a widget scores No Match and logs a warning. Broadcast from the owning actor.

Severity is graded

When a mistake is recorded, its severity reflects what kind of error it was. Using a step of the procedure at the wrong moment is Related (Near Miss): they know the procedure, they got the order wrong. Grabbing a prop that was never part of it is No Match, a different kind of error entirely.

Out Of Order Policy

Four behaviours for acting out of turn
PolicyBehaviourUse for
IgnoreNothing recorded, stay on the step.Free exploration.
Count Mistake (Stay On Step)Record and stay put. The default.Training. Let them find it.
Count Mistake And RestartRecord and go back to step one.Procedures where a wrong order invalidates the result.
Count Mistake And Fail TaskRecord and fail, driving the Failed pin.Assessment.

Restart is the strict one. A single slip on step 5 sends the trainee back to step 1, which is correct for a safety procedure where a wrong order invalidates everything, and merely infuriating everywhere else.

A three-valve startup procedure

The trainee must open valve A, then B, then C. Out-of-order attempts are recorded but should not end the exercise.

Setting up the world

  1. Add the tags

    Control.Valve.A, Control.Valve.B and Control.Valve.C.

  2. Give each valve an identity

    Add a SimFlow Identity to the valve Blueprint, then set each level instance's tag and a Display Name (Valve A and so on).

  3. Make them report neutrally

    In the valve Blueprint, when turned, call Broadcast Flow Event with Event Tag SimFlow.Event.Interact and Payload self.

Setting up the task

  1. Add the task

    A Task node with Task of Ordered Sequence. Event Tag of SimFlow.Event.Interact.

  2. Author the three steps

    Under Steps, click + three times. Step 0 targets Control.Valve.A with the instruction Open valve A, step 1 Control.Valve.B, step 2 Control.Valve.C.

  3. Choose the strictness

    Out Of Order Policy of Count Mistake (Stay On Step). Leave Unlisted Input Is Mistake off, since other props share the interact tag.

  4. Expose progress and score

    Step Blackboard Key of CurrentStep. Score On Success of 25.

  5. Drive the UI

    Bind On Step Completed to tick off a checklist entry, and read Get Current Step Instruction for the on-screen prompt.

    Turning valve C first now records a Related mistake, because the trainee knows the procedure but not the order, while turning an unrelated wheel is ignored.

When it misbehaves

SymptomCause
The task completed instantlySteps is empty, which succeeds by design.
The task failed instantlyEvent Tag is empty.
The task hangs on one stepThat step's Target query is empty, or does not match the object.
Nothing is ever recorded as out of orderThe wrong objects are not in the sequence and Unlisted Input Is Mistake is off, or the policy is Ignore.
Every unrelated prop counts as a mistakeUnlisted Input Is Mistake is on and other actors share the event tag. Turn it off, or use a dedicated tag.
The progress widget is off by oneGet Current Step Index is 0-based.
The sequence keeps restartingThe policy is Count Mistake And Restart.
