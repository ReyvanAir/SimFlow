Task Reference

Wait For Condition Task

Class
USimFlowTask_WaitForCondition
Select via
Task node → Task dropdown → Wait For Condition
Finishes with
Succeeded, once the condition holds
Category
Waiting

Use it for: polling a continuous state. The player is holding the drill, valve rotation is past ninety degrees, the score is high enough.

Where Wait For Event reacts to a discrete moment, this task polls. It can also require the condition to hold for a while, which is how you say "stand still in the safe zone for three seconds".

Fields

USimFlowTask_WaitForCondition, own settings
FieldTypeDefaultMeaning
ConditionInstanced conditionnullThe test to evaluate.
Check IntervalFloat, seconds, min 00.1Seconds between evaluations. 0 evaluates every frame.
Required Hold TimeFloat, seconds, min 00.0The condition must stay true this long before the task succeeds.

Plus the fields every task has.

An empty condition waits forever

This task logs nothing when misconfigured

An unset condition evaluates as false, so the task blocks indefinitely in silence. Wait For Event at least logs and passes through when its tag is missing; this one does not. A task hanging with no log output is usually an empty Condition slot, so check that first.

A condition that is already true when the task starts succeeds almost immediately, after the first check plus the hold time if one is set. Conditions are evaluated from the first check rather than only on a change.

How the interval and hold time interact

The condition is evaluated every Check Interval seconds. While it reads true, hold time accumulates. The moment it reads false, the accumulated hold time resets to zero.

With Check Interval at 0.1 and Required Hold Time at 3.0, that means the condition has to read true on roughly thirty consecutive checks, and a single false reading starts the count over. A flickering condition paired with a hold time may never complete at all.

Raise the interval for expensive conditions

A distance test every frame is cheap. A condition that scans actors is not. But a long interval and a short hold time between them can miss brief windows entirely, so move one at a time and test.

Stand in the safe zone for three seconds

The trainee has to reach the muster point and stay there briefly.

  1. Add the task

    A Task node with Task set to Wait For Condition.

  2. Configure the test

    Condition to Player Near Location, with the muster point's world coordinates, a radius of 200, and Ignore Z on since HMD height varies.

  3. Require them to stay

    Required Hold Time to 3.0, leaving Check Interval at 0.1.

  4. Tell them, and give a way out

    Instruction to Go to the muster point and wait. On the Task node, Time Limit of 60 wired to a hint.

    Stepping out of the radius resets the three seconds. That is intended. They have to actually stay put.

To wait on a flag from another system instead, use Blackboard Compare with key DrillReady, operation ==, value Bool true, and have your Blueprint call Set Bool on the flow's blackboard when it is ready.

When it misbehaves

SymptomCause
The task hangs with nothing loggedThe Condition slot is empty.
The hold time never completesThe condition is flickering. Widen the tolerance with a larger radius or Ignore Z, or lower the hold time.
Performance drops during this taskCheck Interval is 0 with an expensive condition.
A brief event gets missedCheck Interval is too long to catch a short-lived state. Polling is the wrong tool for an instant. Use Wait For Event.
