Node Reference

Join Node

Class
USimFlowNode_Join
Add via
Right-click → Flow Control → Join
Pins
In 0 … In N → Out
Category
Flow Control

Use it for: the question "several things are running and I need one continuation, so when does it fire?"

Join is the partner to Parallel. There are two answers, and they solve quite different problems.

Wait For All

Fires once every connected input has been triggered. Finish both sub-tasks, then continue.

Wait For Any (Race)

Fires on the first input and ignores the rest. This is how you build timeouts and races.

Fields

USimFlowNode_Join, Details panel
FieldTypeDefaultMeaning
Num InputsInt, 2 to 162How many input pins. Values outside the range are clamped.
ModeEnumWait For AllWait For All or Wait For Any (Race).

Pins are named In_0 through In_N, and reducing the count drops those pins along with their links. Something upstream has to produce the branches in the first place: either a Parallel node, or a Branch with Fire All Matching Cases turned on.

What each mode actually does

Wait For All records each arriving input. Once the number of distinct inputs received reaches Num Inputs, it fires Out and deactivates, resetting its counters. That reset is what lets a Join sit inside a Loop and work on every pass.

Inputs count uniquely, so the same pin firing twice counts once. Two arrivals on In_0 will not satisfy a two-input join.

Wait For Any fires Out on the first arrival, then deliberately stays active so it can absorb the losing branch when it turns up. Without that, the downstream section would run a second time.

Matching Num Inputs to reality

This is the one that bites

In Wait For All, if Num Inputs is higher than the number of pins you actually wired, the join can never be satisfied and the flow stalls with nothing in the log. Wire two branches, leave the count at 3, and nothing downstream ever runs.

Set the count to the number of branches you actually wired. A branch that never arrives has the same effect: the join waits forever.

Waiting for both

The trainee must don a helmet and sign the permit before proceeding, in either order.

  1. Fan out

    Add a Parallel node with Num Outputs of 2, and wire each output into its own Task node.

  2. Converge

    Add a Join, Num Inputs of 2, Mode of Wait For All.

  3. Wire both completions

    Each task's Completed into In 0 and In 1, then Out onward.

Racing the clock

The trainee has sixty seconds. Either they finish or the time runs out.

  1. Fan out to work and timer

    A Parallel node: Out 0 into the real task, Out 1 into a Delay node of 60.

  2. Race them

    Add a Join with Mode of Wait For Any (Race), wire both into it, and Out onward.

  3. Record which one won

    Have each branch write a Set Blackboard Value before the join, Outcome = "finished" against "timeout", and read it with a Branch afterwards.

    The join itself does not tell you which input won. Writing a key before the join is the standard way to find out.

When it misbehaves

SymptomCause
Stalled at the join, nothing loggedNum Inputs exceeds the number of branches that actually arrive. Silent by design, so check the count first.
The section after the join ran twiceEither two branches were wired straight into the continuation with no join at all, or Wait For All was used in a situation that wanted Wait For Any.
A join inside a loop only worked on the first passIt should reset when it fires, so check the join is genuinely being re-entered rather than bypassed on later iterations.
Two arrivals on one pin did not satisfy the joinInputs count uniquely. The same pin firing twice counts once.
