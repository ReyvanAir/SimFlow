Node Reference

Parallel Node

Class
USimFlowNode_Parallel
Add via
Right-click → Flow Control → Parallel
Pins
In → Out 0 … Out N
Category
Flow Control

Use it for: things that genuinely happen together. A countdown ticking while the trainee works, ambient narration over a procedure, two independent sub-tasks.

It fires every output at once, so several sections of the graph run at the same time. Pair it with a Join when the branches need to come back together.

The one field

USimFlowNode_Parallel, Details panel
FieldTypeDefaultMeaning
Num OutputsInt, 2 to 162How many output pins. Clamped if you go outside the range.

Changing it rebuilds the pins, which are named Out_0 through Out_N. Reducing the count drops the removed pins and their links; links on the surviving pins are kept.

Unwired pins are skipped, not fired

The node snapshots which pins actually have links and fires only those. An unused output costs nothing, and wiring only some of them is fine.

The flip side is that if you wire none of them, the node finishes without triggering anything and that line of execution quietly ends.

Branches that never converge each run to their own end. If one of them reaches a Finish with Stop Other Branches on, the rest are killed wherever they happen to be.

Parallel is not threaded

Branches are interleaved on the game thread, tick by tick. "Parallel" here means several parts of the graph are active at once, not that anything runs concurrently. Do not rely on ordering within a single tick.

A timer running alongside the work

The trainee performs a procedure while a sixty-second countdown runs. Whoever finishes first ends the section.

  1. Add the Parallel node

    Right-click, then Flow Control → Parallel. Leave Num Outputs at 2.

  2. Wire the work

    Out 0 into the procedure, a Task node running Ordered Sequence.

  3. Wire the timer

    Out 1 into a Delay node set to 60.

  4. Race them

    Add a Join with Mode set to Wait For Any (Race). Wire the end of the procedure into In 0 and the Delay's Out into In 1, then wire the Join's Out onward.

    The Join swallows the loser. Without it, the downstream section would run twice, once per branch.

When it misbehaves

SymptomCause
Only one branch runsThe other pin is not wired. Unwired pins are skipped rather than fired.
The section after the branches ran twiceBoth branches reached it independently. Put a Join in Wait For All mode between them.
A branch was cut off mid-taskSomething downstream hit a Finish with Stop Other Branches on.
Nothing happened at allNo output pin is wired, so the node finished without firing anything.
