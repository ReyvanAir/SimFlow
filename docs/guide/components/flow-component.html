Components

SimFlow Component

Class
USimFlowComponent
Add via
Add Component → SimFlow Component
Goes on
A level actor, the Game Mode, the Game State, the PlayerState or the pawn
One per
Running flow. Two flows at once means two components.

Use it for: running a flow asset. Nothing executes until a component owns it, and everything you start, pause, save or read goes through this one class.

A flow asset is a recipe. The component is the kitchen: it builds a flow instance from the asset, ticks it, fires dispatchers as tasks come and go, and holds the save and score plumbing. Your UI reads the component, your props send events at it, and your Blueprint asks it to start, retry or skip.

Add it, set Flow Asset, pick a Start Mode, and you have a running procedure. Everything else on this page is a knob you may never touch.

Where to put it

The owning actor decides the flow's lifetime and, in multiplayer, who is allowed to run it. Four homes cover almost every project.

Hosting the component
OwnerLifetimeUse when
Level actorThe levelThe scenario belongs to one map. The usual choice, and the easiest to find in the outliner.
Game ModeThe level, server onlyYou want one flow per session and never want a client to hold it.
Game StateThe level, replicatedEveryone is doing the same scenario together and every client needs to see it.
PlayerStateThe playerEach trainee runs their own copy at their own pace.

Putting it on the VR pawn works and is convenient while prototyping, but a pawn gets destroyed and respawned more often than people expect, and the flow goes with it. Move it to a level actor before the scenario matters.

Several components are fine

A machine can run any number of flows at once. Give each one a distinct Flow Save Id and Find Flow By Id will tell them apart. Only one of them is the primary flow, which is the one the no-argument accessors return.

Starting

USimFlowComponent, Details panel · SimFlow and SimFlow | Start
FieldTypeDefaultMeaning
Flow AssetSimFlow AssetNoneThe flow to run. Swap it while stopped to change scenario.
Entry NameNameDefaultWhich Start node to begin from. Only matters when the asset holds several scenarios.
Start ModeEnumManualManual, On Begin Play, On First Tick, or After Delay.
Auto Start DelayFloat (s)1.0Only shown for After Delay.

On Begin Play starts while other actors may still be initialising. If the first task looks for a zone or a prop and sometimes fails on the first run of the level, that is the reason. On First Tick costs you one frame and removes the race, which is why most projects end up there.

Leave it on Manual when a menu, a briefing or an instructor decides the moment. Then call Start Flow, or Start Flow From Entry with the name of the Start node you want.

Driving the run

USimFlowComponent, SimFlow | Control
NodeDoes
Start FlowBegins from Entry Name. False when there is no asset, or one is already running.
Start Flow From EntryBegins from a named Start node.
Stop FlowEnds the run where it stands. No Finish result.
Restart FlowStops and starts again from the top.
Pause Flow / Resume Flow / Toggle PauseFreezes timers and blocks task completion.
Retry Current TaskRe-runs the active task. Fires On Task Retried.
Skip Current TaskCompletes it as skipped and moves on.
Fail Current TaskEnds it as failed, which routes down the failure pin.
Send EventRaises a gameplay tag on this flow, with an optional payload object.
Submit Quiz AnswerAnswers the quiz currently on screen, by option index.

All of these are safe to call from a client. With replication on they forward to the server through the SimFlow Player Component rather than doing the work locally.

Send Event is the one props should use. A valve Blueprint that raises Event.Valve.Closed knows nothing about the procedure, which is what keeps scenario logic out of prop code.

Skip and Fail need gating in multiplayer

Both are ordinary Blueprint-callable functions, so any client can call them on a replicated flow. Hiding the button is not a control. Gate them in Is Request Authorised on the server.

What it tells you

Eleven dispatchers. Bind them on Begin Play in whatever object owns your feedback, and stop polling for state changes.

USimFlowComponent, dispatchers
DispatcherFires when
On Flow StartedA run begins, including after a load.
On Flow Paused / On Flow ResumedPause state changes, from any source.
On Flow FinishedThe run ends. Carries the final state: completed, failed or aborted.
On Task StartedA task becomes active. The hook for updating the instruction panel.
On Task FinishedA task ends, with its result.
On Task RetriedThe same task starts again after a mistake.
On Checkpoint ReachedA Checkpoint node is passed.
On Quiz PresentedA quiz needs answering. Show the panel here.
On New High ScoreA recorded score beat the stored best. Previous best is 0 when there was none.
On Net State ChangedThe replicated summary changed. Clients use this as their general-purpose refresh.

For reading state rather than reacting to it: Get Current Task Name, Get Current Instruction, Get Progress, Get Score, Get Current Task Remaining Time and Get Run State all work on clients too, resolving names and instructions from the flow asset every machine already has. Driving Any Widget has the wiring for a panel that cannot inherit from the SimFlow status widget.

Saving and scenario history

USimFlowComponent, SimFlow | Save and SimFlow | Record
FieldDefaultMeaning
Flow Save IdNoneNames this flow in the save file and over the network. Falls back to the owning actor's name, which changes when someone renames the actor.
Default Save Slot NameSimFlowSaveSlot used by Quick Save and Quick Load.
Auto Resume From Save On Begin PlayfalseResume from an existing save instead of starting fresh.
Default Load ModeExact StateExact State, or From Last Checkpoint.
Scenario Slot NameSimFlowScenariosHistory lives in its own slot, so deleting a save leaves play count and best score standing.
Record Play On FinishtrueCount the attempt and store the outcome automatically.
High Score Requires CompletiontrueOnly a completed run may take the best score. The attempt is counted either way.

Set Flow Save Id on anything you intend to save, address by id, or control from a client. Leaving it None works until someone renames the actor and the save stops matching.

Get Scenario Record, Get High Score and Get Play Count read on any machine, but each call opens the save file. Read once on Begin Play and cache it rather than binding it to a tick or to a widget that refreshes every frame. Scenario Records has the full set.

Save, load and record are authority only. On a client mirror they log and do nothing.

Replication

USimFlowComponent, SimFlow | Network
FieldDefaultMeaning
Replicate FlowfalseServer runs the flow; clients mirror a compact state summary. Read-only at runtime.
Net Refresh Interval1.0 sHow often elapsed time is refreshed. Structural changes replicate immediately.
Replicate BlackboardtrueSend blackboard entries so client UI can read score and answers.

With Replicate Flow off, which is the default, the component behaves exactly as it does in single player. Turn it on and the owning actor has to replicate too, which is why the Game State and the PlayerState are the two homes that work without further thought.

Check Has Flow Authority before doing anything that must happen once, and Is Client Mirror when a branch is presentation only. Replication in the developer guide covers what actually travels.

Debug

Show Debug HUD draws this flow's status on screen. The console variable SimFlow.Debug 1 does the same for every flow at once and is the faster habit. Get Debug Text returns the same content as a multi-line string, which is what to drop into a world-space widget when you are wearing a headset and cannot see the screen HUD.

Follow Game Pause, on by default, pauses the flow when the game pauses. Turn it off for a flow that has to keep timing through a menu.
