Components

SimFlow Player Component

Class
USimFlowPlayerComponent
Add via
Add Component → SimFlow Player Component
Goes on
Your PlayerController Blueprint, and nowhere else
Needed when
Clients have to drive a replicated flow

Use it for: letting a client answer a quiz, press retry, or raise an interaction event on a flow the server owns.

A flow usually lives on the Game State or a level actor, and neither has an owning connection. Unreal will not let a client send an RPC to something it does not own, so without this component a client's button press reaches nothing.

The PlayerController always has a connection. This component sits there and forwards requests to whichever flow the server says owns a given save id.

When you need it

Add it

The flow has Replicate Flow on, and clients press buttons: answering quizzes, retrying a task, an instructor skipping ahead, or props raising events on the client that have to reach the server.

Skip it

Single player. Or a server-authoritative flow that clients only watch, where every control call already happens on the server.

Adding it when you do not need it costs nothing, and it is one component on one Blueprint, so most multiplayer projects add it once and forget about it.

Setting it up

  1. Open your PlayerController Blueprint and add the component

    Add Component → SimFlow Player Component. There is nothing to configure for the common case.

  2. Give every replicated flow a Flow Save Id

    That id is how a request finds its flow on the server. With the id left as None the request goes to the primary flow, which is fine with one flow and wrong with two.

  3. Leave your UI calling the flow component

    Your buttons keep calling Retry Current Task and Submit Quiz Answer on the SimFlow Component. It notices it is on a client and routes through this component for you.

You rarely call this component directly. Request Flow Control and Broadcast Flow Event both find the local one themselves. When you do need the reference, Get Local returns it, or null when the PlayerController has none. The full node list is on Player Component Nodes.

The symptom of a missing component

Nothing crashes. The client's button does nothing, and the log carries a LogSimFlow warning naming the flow and saying the PlayerController has no SimFlow Player Component. That warning is the whole diagnosis.

What goes through it

Client request → server action
RequestServer does
Request ControlStart, Stop, Restart, Pause, Resume, Toggle Pause, Retry, Skip or Fail on the named flow.
Request Quiz AnswerSubmits an answer, addressed by quiz node Guid and option index.
Request EventRaises an event tag. A flow id of None hits every flow.

All three are safe to call on the server too, where they take the direct path instead of an RPC. Save and load are not in the list on purpose: they stay authority only and never travel from a client.

Gating what clients may ask for

Is Request Authorised is a BlueprintNativeEvent that runs on the server for every incoming request, before anything happens. Override it in a Blueprint subclass of the component to write your own rules.

The one field, Restrict To Owned Flows, is the built-in version of the same idea. Off by default. Turn it on and the default check accepts a request only for a flow whose owning actor is this player's own actor, that actor's owner, or an actor this player instigated, which is right for a flow per trainee on the PlayerState and wrong for an instructor driving everyone's scenario.

The flag only gates the default check. Override Is Request Authorised and it does nothing unless your override reads it.

A check in the UI stops an honest player and nobody else

Hiding the skip button does not stop a client from sending the request. Gate Skip, Fail, Stop and Restart here, on the server. A trainee who can skip a task can skip an assessment.

The instructor pattern

One PlayerController Blueprint for trainees, a subclass for the instructor, or a single subclass that reads a role off the PlayerState. Either way the decision lives in Is Request Authorised on the server, and the instructor UI is a UI that sends requests which happen to be accepted.

Keep Restrict To Owned Flows on for the trainee controller and off for the instructor one, then let the override handle the rest.
