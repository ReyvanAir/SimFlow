Chapter 06

Driving UI and VR Feedback

SimFlow ships no widgets and no haptics. It ships the state and the dispatchers, and your UI layer reads them. That is deliberate: a training product's UI is where the house style lives, and a plugin that imposed one would be in the way.

What the plugin does and does not provide

Provided: nine component dispatchers, two more on the flow instance, blackboard change notifications, and a full set of query functions that work on clients. Not provided: widget classes, a CommonUI dependency, haptic effects, audio playback, or objective marker actors. Everything below is a pattern for wiring the first list to the second.

A checklist that updates itself

Two shapes, depending on whether your steps are separate Task nodes or steps inside one Ordered Sequence.

Shape A: one row per Task node

Best when steps are separate graph nodes and may branch. The list is authored in UI, and SimFlow tells you which row is live.

  1. Give every task a Task Id

    Under Presentation, set Task Id to a stable name such as Don.Gloves. This is the key your widget matches on, and it survives renaming the display text or translating it.

  2. Build the row widget

    One BP_ChecklistRow with a Task Id variable, a label, and a state enum of Pending, Active, Done or Failed.

  3. Bind On Task Started

    Read Task Id from the Task pin, find the matching row, set it to Active and set the rest of the pending rows back to Pending.

    Do not assume rows advance in order. A Branch or a remediation loop can jump backwards or skip rows entirely, which is why matching on Task Id beats incrementing an index.

  4. Bind On Task Finished

    Switch on the Result pin: Succeeded to Done, Failed and Timed Out to Failed, Skipped to its own state if you show one.

Shape B: rows inside one Ordered Sequence

Best for "press these three buttons, in this order", where the steps live in one task.

  1. Set Step Blackboard Key on the task

    Set it to CurrentStep. The task then publishes the current step index on every advance.

  2. Bind the blackboard, not a tick

    Get Blackboard, then bind On Value Changed. Filter on the Key pin for CurrentStep and read the index from New Value. No polling, no tick.

  3. Show the live instruction

    Each step carries its own Instruction, readable with Get Current Step Instruction. Use that for the "do this now" line under the list.

  4. Show wrong attempts, if you want to

    WrongAttempts increments on every rejected input and arrives through the same On Value Changed binding, so a "2 errors" counter costs nothing extra.

Objective markers

SimFlow does not place markers. It tells you which object the current step is about, and you place the marker yourself. There are two routes, and which you use depends on how the step targets its object.

Route 1: resolve the identity tag

The step's target is an Actor Query with Required Tags. On On Task Started, read that tag from the task, find actors in the level carrying a matching SimFlow Identity, and attach your marker to them. For a step with several valid targets, mark all of them.

Route 2: read the blackboard

Several tasks publish the object they are about. Place Object In Zone has Placed Item Blackboard Key, which stores the last accepted item. Bind the blackboard's On Value Changed and move the marker when the key changes.

Use Display Name for marker labels

The SimFlow Identity component carries a Display Name text field. Read it with Get Identity Display Name.

Leave it empty and SimFlow falls back to AActor::GetName(), which gives you BP_Extinguisher_C_2. Acceptable in a log, poor floating above a prop in front of a trainee. Set it on anything a trainee might get wrong, because the same field also appears in generated mistake descriptions.

CommonUI

SimFlow has no dependency on CommonUI and no opinion about it. Treat SimFlow as the data source and CommonUI as the presentation stack; the integration is ordinary.

  1. Keep one subscriber, not many

    Bind the dispatchers once, in a controller-side object that outlives individual widgets, then push state into whatever is currently activated. Binding directly from a widget that gets deactivated and reconstructed leaves you chasing stale bindings.

  2. Drive activation from flow state

    On Quiz Presented pushes your quiz widget onto its stack. On Flow Finished pushes the debrief. On Flow Paused and On Flow Resumed are the natural hooks for a pause layer.

  3. Route input back through the component

    A CommonUI button answering a quiz calls Submit Quiz Answer on the component. A "skip" button calls Skip Current Task. Both respect the task's own rules, so an evaluation-mode task with Allow Skip off will refuse, and your button should reflect that rather than assume success.

3D world widgets for VR

In VR, screen-space UI is not an option. Every pattern above works in a Widget Component set to World Space; the only SimFlow-specific advice concerns what to put in them.

World-space widget patterns
WidgetPlace itContent
Instruction boardFixed in the training bay, or wrist-mounted on the pawnGet Current Instruction, refreshed on On Task Started
Wrist checklistAttached to the off-hand controllerShape A or B from above
CountdownNear the target object, not in peripheral visionGet Current Task Remaining Time, hidden when it returns -1
Debug panelBehind the trainee, or on a dev-only rigGet Debug Text, a multi-line status string built for exactly this
Get Debug Text is meant for a VR widget

It returns the same multi-line status the SimFlow.Debug 1 overlay draws: active node, current task, elapsed time, blackboard contents. In VR the console overlay is hard to read, so wiring this into a world-space widget on a developer rig is the practical equivalent.

Motion controller haptics

The plugin plays no haptics. Bind a dispatcher and call Unreal's Play Haptic Effect on the relevant Player Controller and hand. The design question is which signals deserve a pulse, and the answer in training is fewer than you would think: a haptic that fires constantly stops carrying information.

A haptic budget that reads clearly
SignalSourceSuggested feedback
Correct action registered On Task Finished, Result is Succeeded One short confirmation pulse on the acting hand.
Wrong object, near miss On Mistake Recorded, severity Related A soft double pulse. The trainee was close; do not punish the hand.
Wrong object, unrelated On Mistake Recorded, severity No Match A firmer, longer pulse, paired with the on-screen reason.
Step failed or timed out On Task Finished, Result is Failed or Timed Out A distinct low rumble. Do not reuse the mistake pattern.
Checkpoint On Checkpoint Reached Nothing, usually. A visual toast is enough and a pulse here dilutes the others.

Which hand acted is available: On Mistake Recorded carries the involved actor, and your grab system knows which controller is holding it. If you do not track that, pulse both and accept the small loss of precision.

Audio cues

As noted in Chapter 03, tasks carry no sound field in 1.1.4. Drive audio from this layer instead.

  1. Key a Data Table by Task Id

    Rows: Task Id, a narration Sound Base, an optional subtitle text, an optional priority.

  2. Look it up on On Task Started

    Read Task Id from the Task pin, find the row, play the cue. Missing rows should fail silently rather than log, because plenty of tasks will not have narration.

  3. Stop it on On Task Finished

    Or let it run to completion if the next cue queues behind it. Deciding this once, centrally, is much easier than deciding it per task.

    Why not put the sound on the task? Because localisation, mixing and voice direction then live inside flow assets, and a re-record means touching every asset. A table keeps that work in one place, and lets an audio lead work without opening a flow graph.

Score and counters without polling

The blackboard fires On Value Changed on every write. One binding covers score, wrong attempts, step index and anything you write yourself.

Get Blackboard ─▶ Bind Event to On Value Changed
                     │
                     └─▶ Switch on Key
                           "Score"          ─▶ set score text
                           "WrongAttempts"  ─▶ set error count, flash red
                           "CurrentStep"    ─▶ advance checklist row
Score stays at zero until you author it

Score On Success and Score On Failure default to 0.0 on every task. A score widget wired perfectly will display 0 forever if nobody set those values in the flow asset. Check the asset before debugging the widget.

The quiz round trip

  1. On Quiz Presented fires

    It carries the Quiz task. Show your widget.

  2. Read the content

    Get Current Quiz on the component returns the quiz being asked, or null. On clients this is the authored template resolved from the flow asset, which every machine already has.

  3. Submit the answer

    Call Submit Quiz Answer with the index. This is a control call, so it forwards from a client correctly.

    Nothing answers a quiz by itself. A Quiz task hangs forever if no UI ever calls Submit Quiz Answer, and it is the standard cause of "the flow stopped at the quiz".

  4. Read the outcome

    LastAnswerIndex and LastAnswerCorrect land on the blackboard, and Mistakes increments when the task's Count Mistakes is on.

Client UI in multiplayer

What clients can read

Run state, current task, instruction, progress, score, remaining time, current quiz. These resolve names and text from the flow asset locally, so they work without replicating strings.

How to know when to refresh

Bind On Net State Changed. It fires on clients whenever replicated state changes, and the server fires it too, so one code path serves both. Structural changes replicate immediately; elapsed time refreshes on Net Refresh Interval, default one second, which is why a client countdown should interpolate locally rather than display the replicated value raw.

Two things to check when client UI is blank. Replicate Blackboard must be on for score and answers to reach clients. And the PlayerController needs a SimFlow Player Component before any client-side button can reach the server.
