Chapter 02

Core Mental Model and Architecture

SimFlow splits a training scenario into three layers that know almost nothing about each other. Understanding where the boundary sits is what lets you change a procedure without reopening a single prop Blueprint.

The three-part pipeline

Everything in the plugin sits in one of three places, and each tends to have a different owner on a team.

What each layer owns
LayerArtifactAnswers the questionChanging it means
Authoring SimFlow Graph asset What happens, in what order, and what counts as correct Editing an asset. No compile, no Blueprint edits.
Execution USimFlowComponent and its USimFlowInstance Who is running this, from which entry, on which machine Changing component fields in the Details panel.
Feedback Blueprint dispatcher bindings What the trainee sees, hears and feels Editing widget or pawn Blueprints. Procedure logic stays out.

Asset against instance

The flow asset is a template. It holds no runtime state at all. When a SimFlow Component starts a flow it creates a flow instance, then duplicates the asset's nodes and tasks into it.

Two consequences follow, and both come up constantly in practice.

First, two actors can run the same asset independently. A four-trainee exercise with one flow asset on four Player States gives four separate runs with four separate blackboards. Nothing is shared unless you deliberately share it.

Second, editing the asset while the game is running changes nothing, because the instance already holds its own copies. Stop and restart the flow to pick up authoring changes. This surprises people once, then never again.

Where runtime state lives

  • Flow instance: active nodes, elapsed time, run state, event history, recorded mistakes.
  • Blackboard: score, answers, counters, whatever you write.
  • Nodes and tasks: their own per-run state, because they are duplicates.
  • Asset: nothing. It is read-only at runtime.

How the decoupling actually works

The design rule the whole plugin follows is worth stating in one line:

The Blueprint reports neutral facts. The flow asset decides what they mean.

A button broadcasts "I was pressed, by this actor". It does not know whether pressing it was correct, whether it was step 2 or step 5, or whether pressing it early should cost a point. All of that lives in the flow asset.

Compare the two ways to build "press the three valves in order, and penalise the wrong order".

Without the split

Each valve Blueprint holds a step number, checks a shared counter, decides whether the press was in order, and writes to a scoring system. Reordering the procedure means editing three Blueprints. Adding a fourth valve means editing four. A second exercise reusing the same valves means branching the logic inside each one.

With SimFlow

Each valve broadcasts SimFlow.Event.Interact with itself as the payload, and carries an Identity component tagged Control.Valve.One. An Ordered Sequence task in the flow asset lists the expected order and holds the Out Of Order Policy. Reordering the procedure is dragging rows in the Details panel. A second exercise is a second asset. The valves never change.

The same split runs through zones. A SimFlow Zone reports what is inside it and whether each object has settled. It has no opinion about right and wrong. The Place Object In Zone task holds the opinion. It is what lets the same parts bay be the correct answer in one exercise and a distractor in the next, without anyone touching the level.

The four supporting systems

Three layers is the shape. Four systems make the decoupling possible, and they are shared across the whole plugin rather than reinvented per task.

Cross-cutting systems and where they are documented
SystemAnswersWhy it is shared
Identity What is this object? Gameplay tags on a SimFlow Identity component. Replaces "that actor over there" with "any foam extinguisher", which survives spawning, duplication and level streaming.
Actor Query Which object does this task mean? One targeting struct embedded everywhere, so learning it once covers targeting across the plugin. It grades answers rather than returning a bare yes or no.
Blackboard What do we remember across steps? A per-flow key and value store carrying score, answers and counters. Sub Flows merge it, saves serialise it, and UI reads it without polling.
Events How does the world talk to a running flow? Gameplay tags plus an optional payload. Ten props can raise the same tag while knowing nothing about the procedure.

Why match quality matters more than it looks

An Actor Query does not answer yes or no. It grades:

  • Exact Match
  • Related (Near Miss)
  • No Match

That middle value is the reason the tag hierarchy is worth designing carefully. If Item.Extinguisher.Foam and Item.Extinguisher.CO2 share a parent, grabbing the CO2 unit when the foam one was wanted registers as a near miss, and your feedback can say "close, that is the CO2 unit". A flat tag list makes every wrong answer identical, so every mistake reads as total confusion. Designing the tag tree is a design task, not a naming chore.

Where execution actually happens

A flow runs on exactly one machine, called the authority. In single player that is always you. With Replicate Flow on, it is the server, and clients receive a mirror of the state rather than running their own copy.

This matters for the feedback layer. Client widgets read replicated state and resolve names, instructions and quiz content from the flow asset that every machine already has. They do not execute anything. Control calls from a client forward to the server through the local SimFlow Player Component on the PlayerController.

Save and load are authority-only. On a client they log and return, which is deliberate rather than a bug.

Choosing a host actor

  • Game Mode: single-player scenario. Exists before the level's actors do.
  • Level actor: a flow tied to one room or machine.
  • Game State: multiplayer, one shared scenario everyone sees.
  • Player State: multiplayer, one flow per trainee.
  • VR pawn: flows that follow the player across levels, with the caveat that the pawn may respawn.

For replication the host actor has to replicate itself, which is why Game State and Player State are the recommended homes there.

Which layer do I change?

A practical lookup for the question that comes up most on a live project.

Change requests mapped to the layer that owns them
The requestWhat you touchWhat you do not touch
"Swap steps 3 and 4"The flow asset. Reorder the sequence steps or rewire the nodes.Any prop or pawn Blueprint.
"Wrong order should now fail the run"The Ordered Sequence task's Out Of Order Policy.The props raising the events.
"Add a fourth valve to the procedure"An Identity tag on the new valve, plus a step row in the asset.The three existing valves.
"The bay is now a distractor, not the answer"The Accepted Items query on the task.The zone actor in the level.
"Show a countdown for timed steps"A widget bound to On Task Started, reading Get Current Task Remaining Time.The flow asset.
"Give the trainee two retries"The Task node's auto-retry fields, plus the task's Allow Retry.Anything outside the asset.
"Run the same drill inside a longer assessment"A Sub Flow node pointing at the existing asset.The drill asset itself.

If a change request sends you into a prop Blueprint to edit procedure logic, that is the signal something has leaked across the boundary. The usual culprit is a prop that decides correctness instead of reporting a fact.

One run, start to finish

The sequence below is what happens on a single flow. Worth reading once even if you never debug at this level.

  1. Start

    The component creates a flow instance, duplicates the asset's nodes into it, and finds the Start node whose Entry Name matches the component's. Execution leaves that node's Out pin.

    Both default to Default, so renaming one side and not the other breaks the flow in silence. It is the first thing to check when nothing happens at all.

  2. Nodes activate and tick

    Execution arrives at an input pin and the node runs. Task, Delay and Sub Flow nodes stay active and tick every frame. Most nodes ignore execution arriving while they are already active. Join and Loop are built to be re-entered, which is how a loop body returns to its loop node.

  3. Work happens in tasks

    A Task node hands off to its task. The node owns timeout, retry, abort and routing; the task owns the work. Every task therefore gets timeout and retry for free, without implementing either.

  4. The instance broadcasts

    Each transition fires dispatchers on the instance and on the component: task started, task finished with a result, checkpoint reached, quiz presented, event raised, mistake recorded. This is the entire feedback surface.

  5. Finish

    A Finish node ends the run with a result. Execution running out of wiring does not end a flow. The run state stays Running and nothing happens, which is the usual explanation for "the flow never ends".
