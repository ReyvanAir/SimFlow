Blueprint Nodes

Player Component Nodes

Component
USimFlowPlayerComponent
Add via
Add Component → SimFlow Player Component, on your PlayerController
Needed when
Clients have to drive the flow
Category
SimFlow | Network

Use it for: letting a client answer a quiz, press retry, or raise an interaction event on a server-owned flow.

A flow usually lives on the Game State or a level actor, and neither has an owning connection. A client cannot send an RPC to something it does not own, so it cannot talk to the flow directly.

This component sits on the PlayerController, which always has a connection, and forwards requests to whichever flow the server says owns a given save id.

Single player does not need it. A server-authoritative flow that clients only watch does not need it either.

Getting a reference

You rarely need it. Request Flow Control and Broadcast Flow Event both call Get Local internally and fall back sensibly when there is nothing there.

Requests

USimFlowPlayerComponent, client entry points
NodeAsks the server to
Request ControlPerform a control action on the named flow.
Request Quiz AnswerSubmit an answer, by quiz node Guid and option index.
Request EventRaise an event tag. None for the flow id hits every flow.

Request on the first is the same dropdown Request Flow Control uses: Start, Stop, Restart, Pause, Resume, Toggle Pause, Retry Current Task, Skip Current Task, Fail Current Task.

Request Quiz Answer wants the quiz node's Guid rather than a task reference, because that is what replicates. Read it off the current task, or let Submit Quiz Answer on the status widget handle it.

All three are safe to call on the server too. They take the direct path instead of an RPC.

Restrict To Owned Flows

USimFlowPlayerComponent, Details panel
FieldTypeDefaultMeaning
Restrict To Owned FlowsBoolfalseReject requests from a client for flows it does not own.

Off is what you want for instructor controls and not what you want for trainees. The flag only gates the default authorisation check: override that check and it does nothing unless your override honours it.

Gating requests

Is Request Authorised is a BlueprintNativeEvent that runs on the server for every incoming request, before anything happens. Override it in a Blueprint subclass to write your own rules.

A check in the UI stops an honest player and nobody else

Hiding the skip button does not stop a client from sending the request. Gate Skip, Fail, Stop and Restart here, on the server. A trainee who can skip a task can skip an assessment.

The default implementation honours Restrict To Owned Flows and allows everything else.

A trainee controller that can answer but not skip

  1. Create a Blueprint subclass of SimFlow Player Component.
  2. Override Is Request Authorised.
  3. Return false when Request is Skip Current Task, Fail Current Task or Stop; true otherwise.
  4. Add that subclass to your trainee PlayerController.
  5. Give instructors a separate PlayerController with the unmodified component.

Quiz answers and interaction events still go through, so the trainee can do the scenario. They just cannot skip out of it.

When it misbehaves

SymptomCause
Client buttons do nothing and nothing is loggedThe component is not on the PlayerController. The most common multiplayer setup mistake.
Broadcast Flow Event logs a missing player component warningSame cause. On a client the event has nowhere to go.
Requests work as listen server and fail as a clientYou are testing the server path. Run two clients against a dedicated server to exercise the RPC.
Get Local returns null in Event ConstructThe PlayerController may not be ready. Call it later, or bind on possession.
Every client can pause everyone's flowRestrict To Owned Flows is off and Is Request Authorised is not overridden. That is the default.
Quiz answers land on the wrong flowFlow Save Id was left as None, so the server resolved a different flow.
