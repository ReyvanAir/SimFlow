Chapter 03

Authoring Procedures in the Node Graph

The complete node and task inventory, what every pin does, and the metadata fields that feed your tutorial UI. If you read one section here, make it the Task node, because it is the node you will place more than all the others combined.

What every node has in common

Execution arrives at an input pin and leaves through an output pin. Most nodes have a single In and a single Out. The interesting ones have more.

An unwired output pin ends that line of execution

It is not an error, because a flow can legitimately have branches that stop. That is exactly why a misrouted pin fails quietly rather than loudly. When a section of your flow never runs, an unwired pin is the first thing to check.

Every node also carries a Node Comment, a free-form multi-line string drawn on the node in the graph. It is purely for whoever reads the asset next, which on a training project is often a subject-matter expert rather than you.

The node lifecycle

Short, and it explains several behaviours that otherwise look arbitrary.

  1. Execution arrives

    An input pin fires and the node runs its entry logic.

  2. The node may stay active

    Task, Delay and Sub Flow nodes stay active and tick every frame. Others push execution straight out and deactivate.

  3. Execution leaves through an output pin

    Which normally deactivates the node.

    Re-entrancy: most nodes ignore execution arriving while they are already active. Join and Loop are the exceptions, built to be re-entered. That is how a loop body returns to its loop node.

Nodes are duplicated per running flow, so they can safely hold runtime state and two actors can run the same asset independently. It is also why editing an asset mid-play changes nothing until you restart.

The node catalogue

Right-click in the graph to add one. The menu is grouped by the categories below.

Flow Control

Flow Control nodes, with their pins
NodePinsWhat it does, and the field that matters
Start Out Where execution begins. A flow may have several, each with its own Entry Name. The component's Entry Name picks which one runs. Both sides default to Default.
Delay In to Out Waits, then continues. The lighter choice for a bare pause. Use the Delay task instead when you want the Task node's timeout or retry around it.
Branch In to one pin per case, plus Default Takes the first output whose condition passes. Cases evaluate top to bottom, so put the most specific first. Has Default Pin controls whether there is a fallthrough.
Random Branch In to one pin per option Picks one output at random, optionally weighted, with an avoid-repeats option. For varying which scenario variant a trainee gets.
Parallel In to every output at once Fires all outputs simultaneously. This is concurrency in the flow graph, not threading. Converge the branches again with a Join.
Join Several In pins to Out Converges parallel branches. Wait For All or race mode. Num Inputs must match the number of branches you actually wired.
Loop In, Continue to Body, Done Repeats a section. The body must wire back into Continue. Iterations of 0 means "until the break condition passes", guarded by a max-iteration cap.
Finish In Ends the whole flow with a result. Stop Other Branches is on by default, which is the usual cause of a flow ending earlier than expected.
Two wiring mistakes account for most stalled graphs

A Loop whose body never returns to Continue runs its body exactly once and then stops. A Join with Num Inputs set higher than the number of branches that actually arrive waits forever in Wait For All mode, in complete silence. Neither logs anything.

Tasks, Composition, Persistence and Data

The remaining node categories
CategoryNodePinsPurpose
Tasks Task In to Completed, Failed, Skipped, Timed Out Runs a single task. The one you will place most, and the bridge between graph routing and actual work.
Composition Sub Flow In to Completed, Failed Runs another flow asset as a child, merging blackboards. This is what makes flows modular: one drill asset reused inside three assessments.

Data Set Blackboard Value In to Out Writes a blackboard key inline in the graph, without a Task node around it.

The Task node in depth

Class USimFlowNode_Task. Added via right-click, then Tasks → Task.

The division of responsibility is worth stating plainly, because it explains the whole field list: the node handles retry, timeout, early-out and routing. The task handles the work. Every task therefore inherits timeout and retry without implementing any of it.

The four output pins

  • In
  • Completed
  • Failed
  • Skipped
  • Timed Out
When each output pin is taken
PinTaken when
CompletedThe task succeeded.
FailedThe task failed, or was failed from outside by Fail Current Task.
SkippedThe task was skipped, and the task's own Allow Skip permitted it.
Timed OutTime Limit elapsed.

While Fallback To Completed is on, anything left unwired falls back to Completed. It keeps simple linear flows tidy: wire Completed and ignore the rest. Turn the fallback off when a failure must not be allowed to look like a success. With it off, an unwired Failed pin just ends that line of execution.

An empty Task node passes through

Leave the Task slot empty and the node logs "Task node has no task assigned - passing through" and triggers Completed. It does not fail.

This is deliberate. A blocked-out flow full of empty Task nodes still runs end to end, so you can build and test the shape of a scenario before writing a single task. The cost is that a genuinely forgotten task slot looks like success, so you need to know which of the two you are looking at.

Related quiet cases worth committing to memory:

  • A Time Limit of 0 means a task that never finishes blocks the flow forever.
  • An abort condition that is already true when the task starts aborts it on the first frame, because conditions are evaluated from frame one.
  • With every output pin unwired, the fallback takes Completed into nothing and the flow ends there.

A timed step that retries once

The trainee has 30 seconds to press the start button, with one automatic retry before routing to a hint.

  1. Add the node

    Right-click, then Tasks → Task.

  2. Assign the task

    Set Task to Wait For Event with Event Tag set to SimFlow.Event.ButtonPressed.

  3. Set the limit and retries

    Time Limit to 30. Tick Auto Retry On Failure, set Auto Retry Limit to 1, and tick Auto Retry On Timeout so a timeout retries too.

  4. Wire the routes

    Completed onward. Timed Out to a hint section, which is only reached once the retry is used up. Leave Failed and Skipped unwired to fall through.

Tasks are Blueprintable. Create a Blueprint Class from SimFlow Task, override On Task Start for setup, call Finish Task with a result when the work is done, and override On Task End to unbind whatever you bound. Your class then appears in the Task dropdown alongside the built-ins, and inherits retry, skip, timeout, pause and scoring from the node for free.

Step metadata

Three fields on every task exist purely so the rest of your project can describe the step to a human. They come from the task base class and sit above each task's own settings, under Presentation.

Presentation fields, present on every task
FieldTypeDefaultRead back withUse it for
Display NameTextempty Get Current Task Name The short title in the graph, the debug HUD and your checklist widget. Falls back to the class name, which is why an unnamed task shows as SimFlowTask_WaitForEvent in front of a trainee.
InstructionMulti-line textempty Get Current Instruction The objective description. "Pick up the fire extinguisher." This is what a 3D world widget or a subtitle line should display.
Task IdNameNone Recorded on every mistake A stable id so UI and analytics can identify this step across runs. Any recorded mistake carries the Task Id it happened under, which is what makes a debrief report groupable.

Target actor tags for VR interactables

There is no "target actor" field on a task. Targeting is done with an Actor Query, the same struct everywhere it appears, and the field you almost always want is Required Tags.

  1. Tag the interactable

    Add a SimFlow Identity component to the actor. Set Identity Tags to something like Item.Extinguisher.Foam. Set Display Name too, because it appears in generated mistake text.

    Put it on the Blueprint, not the placed instance. Tags added to one level instance do not apply to spawned copies, and that difference stays invisible until a spawned prop stops matching.

  2. Point the task at the tag

    In the task's Actor Query, fill Required Tags with Item.Extinguisher.Foam. Leave Specific Actor and Blackboard Key empty. In the common case you fill in exactly one of those three.

  3. Decide how strict to be

    Require All Tags defaults to true, meaning the actor needs every tag you listed. Set it to false for "any of these". Min Related Tag Depth (default 2) controls how many leading tag nodes count as a near miss.

Which Actor Query field to use
You want to sayFieldSurvives spawning?

"Any foam extinguisher"Required TagsYes. This is the default choice.

An empty query matches nothing

It does not fall through to "match anything". What that means depends on where the query sits: an empty Accepted Items means the task can never complete, an empty Zone means the task fails immediately, and an empty step Target means that step hangs with no complaint. Neither of the silent cases logs anything.

Audio cues

There is no audio cue field on a task in 1.1.4

Tasks carry no sound reference, and the plugin plays nothing itself. Drive audio from the feedback layer instead, which is the right place for it: bind On Task Started, read Task Id or Get Current Task Name, and look the cue up in a Data Table keyed by Task Id. That keeps localisation and audio direction out of the flow asset. Chapter 06 has the wiring.

If you want the cue authored alongside the step rather than in a table, the supported route is a Blueprint task: subclass SimFlow Task, add your own Sound Base property, play it in On Task Start, and stop it in On Task End. Your class then appears in the Task dropdown with the sound field inline, exactly like a built-in.

Node or task?

Several capabilities exist in both forms. There is a Delay node and a Delay task, a Set Blackboard node and a Set Blackboard task. They are not redundant; they trade weight for features.

Choosing between the two forms
Use the node whenUse the task when
It is a simple step in the graphYou want the Task node's timeout, retry or abort handling around it
You want the graph to read clearlyYou want it inside a Parallel Group
You do not need a Failed pinYou want scoring, an instruction, or a Task Id

Rule of thumb

The node forms are lighter, the task forms richer. For a bare pause, the Delay node is the better choice. The moment a step needs to appear in a trainee-facing checklist it has to be a task, because only tasks carry Display Name and Instruction.
